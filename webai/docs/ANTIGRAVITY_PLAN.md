## 0. กฎเหล็ก (ต้องทำตามทุกข้อ)

1. **ห้ามอ่าน/แก้/commit `webai/.env`** (มีความลับจริง) ใช้ `webai/.env.example` เท่านั้น
2. **ห้าม `git push`** และห้ามรันอะไรกับ `chat_history.db` จริง ทดสอบกับฐานข้อมูลชั่วคราวเท่านั้น (`tests/conftest.py` บังคับไว้แล้ว)
3. ห้ามเรียก endpoint ทำลายข้อมูล (`/api/wipe`, ล้าง/ลบทั้งระบบ) ระหว่างทดสอบ
4. ผู้ใช้รันระบบจริงบน Windows เครื่องเดียว (`python app_server.py` พอร์ต 5005, ออกเน็ตผ่าน Cloudflare Tunnel `openchat.sbs`) **แก้ Python แล้วผู้ใช้ต้องรีสตาร์ตเอง** ส่วน static/templates โหลดสดเมื่อรีเฟรช (เปลี่ยน `?v=` ของไฟล์ที่แก้)
5. เครื่อง RAM ตึง (เคย commit memory ~98%): **ห้ามเปิดเซิร์ฟเวอร์ทดสอบค้างหลายตัว** ปิดทุกครั้งหลังทดสอบ
6. การรัน `pytest` ทั้งชุดในคำสั่งเดียวเคยล้มด้วย `OpenBLAS ... Memory allocation failed` ให้รัน **ทีละไฟล์**:
   ```bash
   cd webai
   for f in tests/test_*.py; do VECTOR_BACKEND=python python -m pytest -q -p no:cacheprovider "$f" 2>&1 | tail -1; done
   ```
   ผลอ้างอิงล่าสุด: 34 ไฟล์ผ่านหมด (`test_rag` ข้าม 3, `test_helpers` ไม่มีเคส)
7. ตอบ/คอมเมนต์เป็นภาษาไทยได้ แต่ชื่อฟังก์ชัน/ตัวแปรใช้อังกฤษตามของเดิม
8. ทุกบั๊กที่แก้ต้องมี **ชุดทดสอบที่ล้มก่อนแก้และผ่านหลังแก้** อย่ารายงานว่า "แก้แล้ว" ถ้ายังไม่ได้รันทดสอบ

## 1. ภาพรวมระบบ (ย่อ)

- หลายองค์กร (multi-tenant): `organization_members`, `user_settings.role`, `organization_id` ในตารางส่วนใหญ่
- ชุดทดสอบ: `tests/` (+ `tests/isolated/*_scenarios.py` รันเป็นโปรเซสแยก), เครื่องมือ: `tools/` (`find_undefined_names.py`, `check_sql_schema.py`, `check_frontend_refs.py` ต้องตั้ง `DB_PATH`/`DATA_DIR` ชั่วคราวก่อนรัน)

## 2. รายการปัญหา เรียงตามความสำคัญ

### P0 — ความปลอดภัย

**S1. CSP ยังมี `'unsafe-inline'` ใน `script-src`** ✅ (`app_server.py:422`)
- ผลกระทบ: ถ้ามี XSS เหลือแม้จุดเดียว โค้ดรันได้ทันที (เคยเจอ stored XSS จริงหลายจุดและแก้แล้ว แต่ตรวจครอบคลุมไม่ครบ)
- งาน: ย้าย inline `onclick=`/`onchange=` (หลายร้อยจุดใน `index.html` และ template literal ใน `static/js/*.js`) ไปเป็น `addEventListener` / event delegation (`data-action`) แล้วค่อยเอา `unsafe-inline` ออก ทำเป็นรอบๆ ต่อหน้าจอ ไม่ใช่ทีเดียว
- วัดผล: สคริปต์นับ inline handler ลดลงเรื่อยๆ; เมื่อเอา `unsafe-inline` ออก หน้า/ปุ่มทุกตัวต้องยังทำงาน (ทดสอบด้วย Playwright, ดูข้อ T2)
- ความเสี่ยง: สูง (ปุ่มพังเงียบๆ) ทำหลังข้อ T2 เท่านั้น

**S2. XSS ตรวจไม่ครบทุกหน้า** ⚠️
- ที่ตรวจแล้ว (0 จุดรั่ว): 32 หน้าหลัก + หน้า superadmin ด้วยชุดข้อมูลทดสอบ
- ที่ยังไม่ครอบคลุม: หน้า/หน้าต่างที่ต้องกดปุ่มก่อนเปิด (modal), คลังไฟล์ Drive, ไวท์บอร์ด, เช็คชื่อ, ค่าที่ใส่ใน `onclick="fn('...')"` (ต้องผ่าน `_jsq()`), ชื่อไฟล์อัปโหลดฝั่งเซิร์ฟเวอร์
- วิธีตรวจที่ได้ผล: ดักคำตอบ `fetch` ใน `window.fetch` ให้ฟิลด์ข้อความ/URL ทุกตัวกลายเป็น `<img src=x onerror=...>` แล้วเปิดทุกหน้า + เรียกฟังก์ชัน `load*/render*/open*` ที่ไม่มีพารามิเตอร์ (ดูต้นแบบใน git history หรือเขียนใหม่)
- งาน: ทำเป็นชุดทดสอบอัตโนมัติ (Playwright) รันทุกครั้ง; กรองชื่อไฟล์อัปโหลดด้วย `db/sanitize.clean_label` ที่ฝั่งเซิร์ฟเวอร์; ล้างชื่อเก่าในฐานข้อมูลที่บันทึกก่อนมี sanitizer (สคริปต์ migration ปลอดภัย: สำรองก่อน)

**S3. ผู้สร้างองค์กรได้ role `admin` ระดับ "ทั้งระบบ"** ✅ (`db/orgs.py` ~บรรทัด 369: `UPDATE user_settings SET role='admin'`)
- ต้นเหตุ: ปนกันระหว่างบทบาทในองค์กร (`organization_members.role`) กับบทบาทแพลตฟอร์ม (`user_settings.role`) เคยบรรเทาด้วย `platform_admin_required` แต่ต้นเหตุยังอยู่ และฟังก์ชันอื่นยังตรวจ `role == 'admin'` (เช่น `routes/shared.py` `is_admin()`, `can_*_knowledge_base`)
- งาน: แยกสองบทบาทให้ชัด (คงความเข้ากันได้ย้อนหลัง), ตรวจทุกจุดที่ใช้ `session['role']`/`user_settings.role` ว่าตั้งใจให้เป็นแพลตฟอร์มหรือองค์กร, เขียนชุดทดสอบข้ามองค์กร (owner ขององค์กร A ต้องแตะข้อมูลองค์กร B ไม่ได้ทุก route) — มีต้นแบบใน `tests/test_access_control_isolated.py`
- ความเสี่ยง: สูง กระทบสิทธิ์ผู้ใช้เดิม ต้องมีสคริปต์ย้ายข้อมูลและสำรองก่อน

**S4. Endpoint ที่ส่ง TURN credential** ⚠️ (`/api/webrtc/ice`)
- ส่งให้ผู้ล็อกอินทุกคน (ตั้งใจ) ตรวจว่าไม่ถูกแคชโดย Cloudflare/เบราว์เซอร์ (`Cache-Control: no-store`), มี rate limit

### P1 — ความไม่เสถียรตอนใช้งานจริง

**R1. รันด้วย Werkzeug dev server ใน production** ✅ (`app_server.py:1167`, `allow_unsafe_werkzeug=True`)
- ผล: ล็อกขึ้นคำเตือนทุกครั้ง, ไม่ทนโหลด, จัดการ WebSocket ได้จำกัด
- ตัวเลือก: gunicorn (`gthread` + `simple-websocket`) แบบ **worker เดียว** (สถานะในหน่วยความจำหลายจุดยังเป็น per-process ดูข้อ R2) พร้อมสคริปต์เริ่มระบบสำหรับ Windows (waitress ไม่รองรับ WebSocket)
- งาน: ประเมิน → ทดสอบโหลด/WebSocket → ทำเป็นตัวเลือก (`USE_GUNICORN=1`) ไม่ทับวิธีเดิมจนกว่าจะพิสูจน์ ห้ามทำให้ผู้ใช้เริ่มระบบไม่ได้

**R2. สถานะในหน่วยความจำ: โตไม่หยุด + หายตอนรีสตาร์ต + ใช้ได้เฉพาะโปรเซสเดียว** ✅
- `routes/chat.py`: `_typing_last`, `_rtc_last_offer`, `_profile_cache`, `_pending_calls`; `routes/shared.py`: `online_users_registry` (sid→user)
- ผล: `_typing_last` / `_rtc_last_offer` / `_profile_cache` ไม่เคยลบรายการเก่า (หน่วยความจำรั่วช้าๆ), สายค้าง (`_pending_calls`) หายถ้ารีสตาร์ตกลางสาย (ยอมรับได้ แต่ควรบันทึกว่าเป็นข้อจำกัด), ถ้าเพิ่มจำนวน worker ทุกอย่างพัง
- งาน: เพิ่มการกวาดรายการหมดอายุ (เช่น ทุก 5 นาทีในงานเบื้องหลังที่มีอยู่) + ชุดทดสอบ; ถ้ามี `REDIS_URL` ให้ใช้เก็บแทน (มีตัวกันหลาย worker อยู่แล้วที่ `app_server.py:327`)

**R3. "database is locked" เมื่อมีงานเบื้องหลังชนกัน** ✅ (เห็นซ้ำตอนรัน fuzz; `busy_timeout=60000` ตั้งไว้แล้วที่ `db/connection.py:459`)
- ต้นเหตุที่น่าสงสัย: งานเบื้องหลังหลายตัว (`_scheduled_line_inbox_recover` ทุก 1 นาที, sync Drive, สรุปรายวัน, ฯลฯ) + การเขียนจากหลายเธรดขณะมีโปรเซสอื่น (เซิร์ฟเวอร์ทดสอบ) ใช้ไฟล์ DB เดียวกัน; การเปิด/ปิดคอนเนกชันถี่ๆ
- งาน: วัดว่าล็อกมาจากงานไหน (เพิ่ม logging ระยะเวลาถือล็อก), ลดความถี่/ทำงานเป็นชุด, ใช้ transaction สั้นๆ, ตรวจคอนเนกชันที่ลืมปิด/ลืม commit (เคยเจอใน `tools/fuzz_routes.py`)

**R4. คอขวดประสิทธิภาพของแชท** ✅ (บางส่วนแก้แล้ว)
- แก้แล้ว: เช็คสมาชิกห้องด้วยคำสั่งเบา, รายการแชทใช้ดัชนี (630ms → 25ms ที่ 100k ข้อความ)
- ยังค้าง: เปิดแชทไว้ระบบโพลล์ **ทุก 3 วินาที** (`startChatPolling` ใน `chat.js`) และ `renderChatMessages` วาด HTML ทั้งแชทใหม่ทุกครั้งที่ข้อมูลเปลี่ยน (เทียบด้วย `JSON.stringify` ทั้งอาร์เรย์) → แชทยาวๆ ช้า/กินเครื่อง; ไม่มี pagination ของ `get_room_messages`/`get_dm_history`
- งาน: ดึงเฉพาะข้อความใหม่ด้วย `since_id`, วาดต่อท้ายแทนวาดใหม่ทั้งหมด, แบ่งหน้าเมื่อเลื่อนขึ้น, ลดการโพลล์เมื่อซ็อกเก็ตเชื่อมต่ออยู่ (ซ็อกเก็ตเป็นตัวหลัก โพลล์เป็นตัวสำรองทุก 30–60 วินาที) พร้อมชุดทดสอบเทียบผลเดิม

**R5. ความเสถียรของระบบโทร** 🔧
- ที่ทดสอบจริง (สองแท็บ + สื่อจำลอง): โทรวิดีโอ/เสียง, แชร์จอ, เปิดกล้องกลางสาย, โทรหาคนที่ยังไม่เปิดแอป (สายค้าง 45 วินาที), ขยายเสียง
- **ยังไม่ได้ทดสอบ:** ไมค์/กล้อง/ลำโพงจริง, โทรข้ามเครือข่าย (ต้องตั้ง TURN: Cloudflare/Metered ใน `.env` ดู `webrtc_ice.py`), push notification จริง (เบราว์เซอร์ทดสอบบล็อกการแจ้งเตือน), iPhone (ต้องติดตั้ง PWA), เบราว์เซอร์ Safari/Firefox
- งาน: เขียนรายการทดสอบด้วยมือสำหรับผู้ใช้ (checklist) + Playwright แบบสองบริบท (Chromium `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream`) ครอบคลุมโฟลว์เดียวกัน
- ข้อจำกัดที่ต้องบอกผู้ใช้: เว็บทำสายเข้าเต็มจอแบบแอปโทรศัพท์ไม่ได้ ทำได้แค่แจ้งเตือน push

**R6. Service worker / แคชไฟล์เก่า** ⚠️
- เวอร์ชันไฟล์เป็น `?v=` ที่ต้องแก้มือทุกครั้ง (ลืม = ผู้ใช้เห็นของเก่า) และ `CACHE_NAME = 'orgchat-offline-v13'` ใน `static/sw.js`
- งาน: สคริปต์คำนวณ hash เนื้อหาใส่ `?v=` อัตโนมัติ (หรือ build step) + ทดสอบว่าหลังแก้ไฟล์ผู้ใช้ได้รุ่นใหม่

**R7. Tailwind คอมไพล์ล่วงหน้า: คลาสที่ประกอบตอนรันจะไม่มีสไตล์** ⚠️ (`tools/tailwind/README.md`)
- งาน: สคริปต์ตรวจ (build ใหม่แล้วเทียบ / สแกนหาสตริงที่ประกอบด้วย `${}` แล้วมีคำนำหน้าคลาส Tailwind) ใส่ใน CI; ถ้าเจอใส่ `safelist` เฉพาะตัว (ห้ามใส่ pattern กว้าง จะทำให้ build ช้าและ CSS บวม)
