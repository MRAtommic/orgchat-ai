# แผนงานสำหรับ Antigravity: ให้บอต RAG เข้าใจ "คำถามติดตาม" และตอบเรื่องข้อมูลติดต่อให้ครบ

- ห้ามทดสอบกับ `chat_history.db` จริง และห้ามเขียนทับคลังความรู้จริง (`chroma_db_fallback.json`, `file_meta.json`) ใช้ `DB_PATH`, `DATA_DIR` ชี้ไปโฟลเดอร์ temp และ `VECTOR_BACKEND=python`, `AI_EMBEDDING_PROVIDER=local` (ดูตัวอย่าง `tests/isolated/google_oauth_scenarios.py`, `tests/isolated/kb_concurrent_ingest_scenarios.py`)

- รายงานเป็นภาษาไทย ตรงไปตรงมา ส่วนที่ทดสอบกับโมเดลจริงไม่ได้ให้บอกชัด อย่าอ้างว่าได้ผลถ้าไม่ได้ทดสอบ ผู้ใช้ต้องรีสตาร์ตเซิร์ฟเวอร์หลังแก้ Python

ผู้ใช้ถามบอตในเว็บแชทว่า "ขอเบอร์ติดต่อบริษัทหน่อย" บอตตอบว่าไม่พบเบอร์ ผู้ใช้ถามต่อว่า "ทำไมจะไม่มีไปเช็คดู" บอตตอบว่าระบบมีแค่รายชื่อพนักงานและอีเมลภายใน
ผลตรวจคลังความรู้ (อ่านอย่างเดียว) พบว่า `ประวัติบริษัท_Chuenchob.txt` มีหัวข้อ "7. ข้อมูลการติดต่อ" ซึ่งมี **อีเมล contact@chuenchob.co.th และ LINE OA @chuenchob** ส่วนเบอร์โทรเป็นตัวอย่าง `02-XXX-XXXX` ที่ยังไม่ได้ใส่เลขจริง (เป็นปัญหาของข้อมูล ผู้ใช้ต้องแก้ไฟล์ต้นฉบับเอง ไม่ใช่งานของ anti)

## ปัญหาในโค้ดที่พบ
1. **ค้นเอกสารด้วยข้อความล่าสุดอย่างเดียว:** `rag_engine.retrieve_context(question, where)` ถูกเรียกด้วย `user_text`/`question`/`text` ตรงๆ (`routes/chat.py` ~บรรทัด 1278 และ ~1744, `routes/line_webhook.py` ~3588, 3706, 3714, `routes/features.py` ~885) ไม่ใช้บริบทบทสนทนาก่อนหน้า ประโยคติดตามสั้นๆ เช่น "ทำไมจะไม่มีไปเช็คดู", "แล้วอีเมลล่ะ", "อันนั้นเท่าไหร่" จึงไม่มีคำสำคัญให้ค้นเจอ เอกสารที่ถูกดึงมาไม่เกี่ยวข้อง บอตจึงตอบมั่วหรือปฏิเสธ
2. **คำตอบไม่ใช้ข้อมูลที่ดึงมาครบ:** รอบแรกเอกสารถูกดึงมาแล้ว (มีไฟล์ประวัติบริษัทในแหล่งอ้างอิง) แต่บอตสรุปว่า "ไม่พบเบอร์" โดยไม่บอกอีเมล/LINE OA ที่อยู่ในหัวข้อเดียวกัน
3. ตอนไม่พบข้อมูลที่ต้องการ บอตยังกล่าวอ้างเกี่ยวกับสิ่งที่ "ระบบมีอยู่" ซึ่งไม่ตรงกับคลังจริง (ไม่ควรสรุปขอบเขตของข้อมูลทั้งระบบจากท่อนที่ค้นมาไม่กี่ท่อน)

## งานที่ 1: เขียนคำถามติดตามให้สมบูรณ์ก่อนค้น (Query Rewriting) — งานหลัก
**แนวทาง:** เพิ่มฟังก์ชันกลาง เช่น `rag_engine.build_search_query(question, history)` (หรือไฟล์ตัวช่วยใหม่ `rag_query.py`) ที่คืนข้อความสำหรับค้น
1. ถ้าข้อความใหม่ **ยาวพอและมีคำสำคัญของตัวเอง** (เช่น ≥ ~25 ตัวอักษรไทย หรือไม่ขึ้นต้นด้วยคำเชื่อม/สรรพนาม/คำอ้างอิง เช่น "แล้ว", "อันนั้น", "ทำไม", "ล่ะ", "เหมือนกัน", "นั้น") ให้ใช้ข้อความเดิม ไม่ต้องเรียก AI เพิ่ม (ประหยัดโควตา/เวลา)
2. ถ้า **สั้นหรือเป็นประโยคติดตาม** ให้ประกอบคำค้นจาก "คำถามผู้ใช้ก่อนหน้า 1–2 ข้อความล่าสุด + ข้อความใหม่" ด้วยกติกาแบบกำหนดตายตัวก่อน (เร็ว ไม่พึ่ง AI): ต่อข้อความผู้ใช้ก่อนหน้าเข้ากับข้อความใหม่ (จำกัดความยาวรวม ~300 ตัวอักษร ตัดซ้ำ) เป็นตัวเลือกพื้นฐานที่ต้องมีเสมอ
3. (ทางเลือกขั้นสูง ทำเมื่อข้อ 2 เสร็จและเทสต์ผ่าน) ให้ LLM เขียนคำถามใหม่ให้ครบความด้วยพรอมต์สั้นๆ ("เขียนคำถามล่าสุดให้เป็นประโยคสมบูรณ์ที่เข้าใจได้โดยไม่ต้องอ่านบทสนทนา ตอบเป็นประโยคเดียว") เฉพาะกรณีที่ข้อ 1 ตัดสินว่าเป็นประโยคติดตาม ตั้ง timeout สั้น ถ้าล้มเหลวให้ถอยกลับไปใช้ข้อ 2 เสมอ **ห้ามให้ความล้มเหลวของการเขียนใหม่ทำให้แชทพัง**
4. ใช้คำค้นที่ได้เฉพาะ **การค้นเอกสาร** เท่านั้น ส่วนข้อความที่ส่งให้ LLM ตอบยังเป็นข้อความต้นฉบับของผู้ใช้ + ประวัติบทสนทนาเดิม
5. นำไปใช้ในจุดเรียกทั้งหมด: `routes/chat.py` (เว็บแชท AI ทั้งสองจุด), `routes/line_webhook.py` (LINE, มีประวัติจาก `database.get_history` อยู่แล้ว ~บรรทัด 3667), `routes/features.py` ถ้าเข้าข่ายเป็นแชทต่อเนื่อง
6. ประวัติที่ใช้ต้อง **จำกัดตามผู้ใช้/ห้องเดียวกัน** (ห้ามดึงประวัติของผู้ใช้อื่นมาปนในคำค้น) และใช้ตัวกรองสิทธิ์เดิม (`get_rag_filter`) ตามเดิมโดยไม่เปลี่ยน
**ทดสอบ (mock LLM และ embedding ใช้แบบ local กับ temp DATA_DIR):**
- เตรียมเอกสารตัวอย่างที่มี "ข้อมูลการติดต่อ: อีเมล…, LINE OA…" และเอกสารอื่นที่ไม่เกี่ยวข้อง
- ลำดับ "ขอเบอร์ติดต่อบริษัทหน่อย" → "ทำไมจะไม่มีไปเช็คดู": ท่อนที่เกี่ยวกับข้อมูลติดต่อต้องอยู่ในผลค้นของข้อความที่สอง (ก่อนแก้ต้องไม่อยู่ ให้เขียนเทสต์ที่ล้มก่อนแล้วผ่านหลังแก้)
- ข้อความยาวที่มีคำสำคัญครบ ต้องไม่ถูกดัดแปลง
- ประวัติว่าง/ข้อความแรกของห้อง ต้องไม่พัง
- ผู้ใช้ A กับ B ห้ามปนประวัติ
- ถ้าเรียกตัวเขียนใหม่ด้วย LLM ล้มเหลว (mock ให้ raise) ต้องถอยกลับไปใช้คำค้นแบบต่อข้อความและแชทยังตอบได้

## งานที่ 2: ให้คำตอบใช้ข้อมูลที่ดึงมาครบ และไม่กล่าวเกินจริงเมื่อไม่พบ
**แนวทาง:** ปรับ system prompt ของบอต (ค้นข้อความพรอมต์ใน `routes/chat.py` และ `routes/line_webhook.py` ซึ่งมีหัวข้อ "หากถามข้อมูลองค์กรแต่ไม่มีในระบบจริงๆ") เพิ่มกฎสั้นๆ:
1. ถ้าท่อนที่ดึงมามีข้อมูลที่เกี่ยวกับคำถามบางส่วน (เช่นมีอีเมล/LINE OA แต่เบอร์เป็นตัวอย่าง `XXX-XXXX`) ให้ตอบส่วนที่มี และบอกชัดว่าส่วนไหนยังไม่มีข้อมูลจริงในเอกสาร
2. ห้ามสรุปว่า "ในระบบมีแค่…" หรือ "ระบบไม่เก็บ…" กับสิ่งที่ตนไม่ได้เห็นทั้งคลัง ให้บอกเพียงว่า "ในเอกสารที่ค้นพบตอนนี้ไม่มี…" แล้วแนะนำช่องทางถัดไปที่มีจริงในเอกสาร
3. เลขโทรศัพท์ที่เป็นตัวอย่าง (`XXX`, `0X-`) ให้ถือว่าไม่ใช่เบอร์จริง
**ข้อควรระวัง:** อย่าทำให้บอตเริ่มแต่งข้อมูลขึ้นเอง (กฎเดิม "ห้ามสร้างข้อมูลเท็จ" ต้องคงไว้) และไม่ลดความเข้มข้นของการป้องกัน prompt injection ที่มีอยู่
**ทดสอบ:** ตรวจว่าพรอมต์ใหม่ถูกประกอบเข้าไปจริง (เทสต์หน่วยตรวจข้อความพรอมต์) เนื่องจากไม่มีโมเดลจริงในเครื่องทดสอบ ต้องบอกผู้ใช้ตรงๆ ว่าคุณภาพคำตอบจริงต้องลองกับ Gemini/Groq ของผู้ใช้เอง และเตรียมรายการคำถามทดสอบให้ผู้ใช้ลอง (ดูข้างล่าง)

## งานที่ 3: เครื่องมือตรวจว่าเอกสารมีข้อมูลตัวอย่างค้างอยู่ (ทางเลือก ทำถ้ามีเวลา)
เพิ่มคำสั่ง/หน้าแอดมินแบบอ่านอย่างเดียว ที่สแกนคลังความรู้หาข้อความตัวอย่างที่ยังไม่ได้แก้ เช่น `XXX-XXXX`, `0X-XXX`, `example@`, `ชื่อบริษัท…`, `[ใส่…]` แล้วแสดงชื่อไฟล์และบรรทัดที่พบ เพื่อให้ผู้ดูแลกลับไปแก้เอกสารต้นฉบับ (เคสนี้ปัญหาต้นเหตุคือเอกสารยังมี `02-XXX-XXXX`) ห้ามแก้เอกสารเองอัตโนมัติ

## รายการคำถามให้ผู้ใช้ลองเองหลังแก้ (ต้องใช้โมเดลจริง)
1. "ขอเบอร์ติดต่อบริษัทหน่อย" แล้วต่อด้วย "แล้วอีเมลล่ะ", "ทำไมจะไม่มีไปเช็คดู", "LINE ล่ะ"
2. "บริษัทก่อตั้งปีไหน" แล้วต่อด้วย "แล้วใครเป็นผู้ก่อตั้ง"
3. "ลาป่วยได้กี่วัน" แล้วต่อด้วย "ต้องแนบอะไรไหม"
4. คำถามที่ไม่มีในเอกสารเลย ต้องตอบปฏิเสธสุภาพ ไม่แต่งข้อมูล

## เกณฑ์ที่ถือว่าเสร็จ
1. เทสต์ใหม่ผ่าน (รวมเทสต์ที่ล้มก่อนแก้แล้วผ่านหลังแก้) และเทสต์ RAG/แชทเดิมผ่านทีละไฟล์
2. คำถามติดตามสั้นๆ ค้นเจอเอกสารเรื่องเดียวกับคำถามก่อนหน้า (พิสูจน์ด้วยเทสต์ที่ไม่ใช้โมเดลจริง)
3. ไม่มีการเรียกบริการภายนอกจริงระหว่างทดสอบ
4. รายงานสรุปภาษาไทย: แก้อะไร/ไฟล์ไหน/ทดสอบอะไร/อะไรต้องให้ผู้ใช้ลองกับโมเดลจริง/ต้องรีสตาร์ตเซิร์ฟเวอร์

## งานที่ 4: LINE พิมพ์ "ค้นหา รายชื่อ" แล้วได้รายชื่อพนักงานเป็นข้อความ ไม่ได้ไฟล์/ลิงก์ไฟล์ (ผู้ใช้รายงานเพิ่ม)
**สาเหตุที่พบ (`routes/line_webhook.py`):**
1. ~บรรทัด 2776–2778 "Staff Directory quick query": ข้อความที่มีคำว่า `รายชื่อ/สมาชิก/พนักงาน` ร่วมกับ `ค้นหา/ดู/ขอ/เช็ค…` ถูกตอบเป็นรายชื่อสมาชิกองค์กรทันที ก่อนถึงโค้ดค้นหาไฟล์ ทำให้ "ค้นหา รายชื่อ" ไม่เคยไปค้นไฟล์
2. ~บรรทัด 2813–2815 `is_directory_intent` (มี `รายชื่อ, พนักงาน, สมาชิก, เบอร์โทร, เบอร์, ติดต่อ, ทีมงาน`) ทำให้ `is_file_query = not is_directory_intent and ...` เป็นเท็จเสมอ แม้พิมพ์ "ค้นหาไฟล์รายชื่อ" ก็ไม่เข้าการค้นไฟล์
3. ข้อความแนะนำของบอตเอง (~บรรทัด 2956, 3068) บอกให้พิมพ์ `'ค้นหา รายชื่อ'` เพื่อค้นไฟล์ ซึ่งขัดกับข้อ 1–2
**แนวทางแก้:**
- คำที่ขึ้นต้นด้วยตัวกระตุ้นการค้นหาไฟล์ที่ชัดเจน (`ค้นหาไฟล์`, `หาไฟล์`, `ดูไฟล์`, `ขอดูไฟล์`, `search file`) ต้องไปค้นไฟล์ก่อนเสมอ ไม่ว่ามีคำว่ารายชื่อหรือไม่
- ข้อความรูปแบบ `ค้นหา <คำ>` (ปุ่ม Rich Menu "ค้นหาไฟล์" ส่ง `ค้นหา ` มา): ให้ค้นไฟล์ (KB + drive_logs + Drive) ก่อน ถ้าเจอให้ตอบรายการไฟล์พร้อมลิงก์เปิดในระบบ/ดาวน์โหลด (โค้ดจัดรูปแบบอยู่แล้วที่ ~บรรทัด 2935–2960) ถ้าไม่เจอเลยและมีคำเกี่ยวกับรายชื่อ/พนักงาน ค่อยถอยกลับไปตอบรายชื่อสมาชิก
- ข้อความที่ไม่ได้ขึ้นต้นด้วย "ค้นหา/หาไฟล์" เช่น "รายชื่อพนักงาน", "ใครบ้าง", "เบอร์พี่ฟิว" ยังตอบรายชื่อ/ข้อมูลติดต่อเหมือนเดิม
- ตรวจสิทธิ์ `check_line_user_permission(..., "search", ...)` เหมือนเดิม และ **ไฟล์ที่มีข้อมูลส่วนบุคคล (เช่น รายชื่อ.txt, salary.data.csv) ต้องผ่านตัวกรองสิทธิ์หมวดหมู่ตามผู้ใช้** อย่าให้ลิงก์ไฟล์เงินเดือนหลุดไปยังผู้ใช้ที่ไม่มีสิทธิ์ (ตรวจว่าตัวค้นไฟล์ใช้ `get_rag_filter`/สิทธิ์หมวดหมู่หรือไม่ ถ้าไม่ ให้เพิ่ม)
- แก้ข้อความแนะนำให้ตรงกับพฤติกรรมจริง
**ทดสอบ (mock LINE API ห้ามเรียกจริง):** "ค้นหา รายชื่อ" → ได้รายการไฟล์ที่ชื่อมี "รายชื่อ" พร้อมลิงก์; "ค้นหาไฟล์รายชื่อ" → เหมือนกัน; "รายชื่อพนักงาน" → ยังได้รายชื่อสมาชิก; "ค้นหา ซักๆ ที่ไม่มีไฟล์" → ข้อความไม่พบไฟล์ไม่ใช่รายชื่อสมาชิก; ผู้ใช้ที่ไม่มีสิทธิ์ห้ามเห็นไฟล์ในหมวดที่ถูกจำกัด
