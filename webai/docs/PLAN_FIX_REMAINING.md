## ข้อ 1: ผู้ใช้ถูกเด้งออกจากระบบเมื่อเบราว์เซอร์อัปเดตเวอร์ชัน
**ตำแหน่ง:** `app_server.py` ฟังก์ชัน `_get_ua_fingerprint` (~บรรทัด 499) และจุดเทียบ `_ua_hash` (~บรรทัด 579)
**สาเหตุ:** fingerprint = `platform:browser:major` มีเลขเวอร์ชันหลักของเบราว์เซอร์ด้วย Chrome อัปเดต 120→121 = fingerprint เปลี่ยน = ถูกเตะออก (docstring บอกว่า "ทนต่อการอัปเดตเวอร์ชัน" แต่โค้ดจริงไม่ทน)
**แนวทางแก้:**
1. ตัดเลข `major` ออกจาก fingerprint ให้เหลือ `platform:browser` (ยังจับการขโมยคุกกี้ข้ามเครื่อง/ข้ามระบบปฏิบัติการได้เหมือนเดิม)
2. **เซสชันเดิมที่เก็บค่าแบบมีเวอร์ชันไว้ต้องไม่ถูกเตะทั้งระบบ** ตอนเทียบ: ถ้า `stored_ua` ขึ้นต้นด้วย fingerprint ใหม่ (เช่น `windows:chrome:120` เริ่มด้วย `windows:chrome`) ให้ถือว่าตรงและเขียนทับด้วยค่าใหม่แบบไม่มีเวอร์ชัน
3. อัปเดต docstring ให้ตรงกับพฤติกรรมจริง
**ทดสอบ:** ปรับ/เพิ่มสถานการณ์ใน `tests/isolated` (แบบอย่าง: `scratchpad session_demo.py` หัวข้อ 2)
- Chrome/120 → Chrome/121 บน Windows เดิม = ยังล็อกอินอยู่
- คุกกี้เดียวกันจาก iPhone Safari = ถูกปฏิเสธ (ต้องยังจับได้)
- เซสชันเก่าที่เก็บเป็น `windows:chrome:120` แล้วมาด้วย Chrome 121 = ยังอยู่ และถูกอัปเกรดเป็นรูปแบบใหม่
- เทสต์ session/auth ที่มีอยู่ทั้งหมดต้องยังผ่าน (รันทีละไฟล์)

## ข้อ 2: `validateTaxIdLive` "ไม่มีนิยาม"
**ตำแหน่ง:** `templates/tax_expense_dashboard.html` — เรียกที่บรรทัด ~813, นิยามที่ ~1035, ผูก `window.validateTaxIdLive` ที่ ~1061
**หมายเหตุสำคัญ:** รอบตรวจล่าสุดพบว่า **มีนิยามอยู่ในไฟล์นี้แล้ว** แต่ที่เคยแจ้งว่า undefined อาจเป็นหน้าอื่น หรือสคริปต์ถูกโหลดช้ากว่า `oninput` หรือถูกครอบด้วยบล็อกที่ error ก่อนถึงบรรทัด 1061
**สิ่งที่ต้องทำ (ตรวจก่อนแก้ ห้ามเดา):**
1. `grep -rn validateTaxIdLive static templates` ดูว่ามีใครเรียกจากที่อื่นโดยไม่มีนิยามบ้าง (โดยเฉพาะ `templates/index.html` และ `static/js/*.js`)
2. เปิดหน้า tax_expense_dashboard ในเบราว์เซอร์ทดสอบ ดู Console ว่ามี `ReferenceError` หรือ error ก่อนถึงบรรทัด 1061 ไหม พิมพ์เลข 13 หลักถูก/ผิดในช่อง `modalField-taxId` ดูว่า validate ทำงาน
3. ถ้าพบจุดที่เรียกโดยไม่มีนิยาม: เพิ่มนิยามกลางใน JS ที่หน้านั้นโหลดแน่ๆ (อัลกอริทึมเลขผู้เสียภาษี 13 หลักไทย: ตรวจ checksum หลักที่ 13) หรือย้ายไปไฟล์ร่วมแล้วให้ทุกหน้าใช้ตัวเดียว
4. ถ้าไม่พบปัญหาจริง ให้รายงานผู้ใช้ตามจริงว่า "ตรวจแล้วไม่มีบัค" อย่าแก้ส่งเดช
**ทดสอบ:** เลขถูก (checksum ผ่าน) = แสดงถูกต้อง, เลขผิด/ไม่ครบ 13 หลัก = แจ้งเตือน, ช่องว่าง = ไม่ error, Console สะอาด

## ข้อ 3: ข้อมูลลงเวลา (time_attendance) เก่าบางแถวคลาด 7 ชั่วโมง
**ตำแหน่ง:** ตาราง `time_attendance` (`db/schema.py` ~บรรทัด 79: `check_date`, `check_time`, `created_at`), `tz_fix.py`, `routes` ที่บันทึกเช็คชื่อ
**ที่มา:** ก่อนมี `tz_fix.py` เซิร์ฟเวอร์บน Windows ถือ TZ เป็น UTC ทำให้บางแถวบันทึก `check_time` เป็นเวลา UTC (ช้ากว่าไทย 7 ชม.) และตัดสิน `on_time/late` ผิด
**ข้อควรระวังสูงสุด:** นี่คือการแก้ข้อมูลจริงของผู้ใช้ **ห้ามแก้ตรงๆ กับ `chat_history.db` จริงโดยไม่ได้รับอนุญาต**
**แนวทาง:**
1. เขียนสคริปต์ **อ่านอย่างเดียว** `tools/audit_attendance_tz.py` ที่รับพาธ DB เป็นอาร์กิวเมนต์ แล้วรายงาน: แถวไหนน่าจะคลาด (เช่น `check_time` อยู่นอกช่วงเวลาทำงานสมเหตุสมผล เช่น 00:00–05:00 ขณะที่ `created_at` ต่างจาก `check_date+check_time` ~7 ชม.) ระบุช่วงวันที่ที่เริ่มใช้ `tz_fix` (ดูจาก git/log หรือถามผู้ใช้) อย่าเดาเอง
2. ทดสอบสคริปต์กับ DB ชั่วคราวที่สร้างข้อมูลจำลองคลาด/ไม่คลาด
3. ทำสคริปต์แก้ `tools/fix_attendance_tz.py` แบบ **dry-run เป็นค่าเริ่มต้น** (แสดงสิ่งที่จะแก้ ไม่แก้จริง) ต้องใส่ `--apply` ถึงจะแก้ และ **สำรองไฟล์ DB อัตโนมัติก่อนแก้** แก้เฉพาะแถวที่ผ่านเกณฑ์ชัดเจน คำนวณ `status` (on_time/late) ใหม่จากกติกาใน `org_attendance_settings`
4. **หยุดแล้วรายงานผู้ใช้** พร้อมรายการแถวที่จะแก้ ให้ผู้ใช้ตัดสินใจเองก่อนรัน `--apply` กับ DB จริง (อย่ารันเอง)
**ทดสอบ:** DB ชั่วคราว — dry-run ไม่เปลี่ยนข้อมูล, apply แก้เฉพาะแถวที่คลาด, รันซ้ำ (idempotent) ไม่แก้ซ้ำ, ไฟล์สำรองถูกสร้าง

## ข้อ 4: `knowledge_harvester.py` มีปัญหา import / SQL
**พบแล้ว:**
- `create_wiki_draft` ใช้ `from .database import _get_conn` (relative import) แต่ไฟล์ถูก import แบบ top-level (`app_server.py:69: from knowledge_harvester import ...`) → เรียกฟังก์ชันนี้จะ error `attempted relative import with no known parent package` และถูก `try/except` กลืนเงียบหรือพังตอนเรียก
- `analyze_recent_messages` ดึงจากตาราง `messages` (`db/schema.py` ~109) ซึ่งมีคอลัมน์ `username, role, text, sources, timestamp` — **ต้องตรวจว่ามีคอลัมน์ `organization_id` จริงไหม** (ถ้าไม่มี SQL นี้ error) และตาราง `messages` คือแชทกับ AI ไม่ใช่ข้อความกลุ่ม LINE ตามที่ prompt อ้าง
- `wiki_pages` ถูกประกาศ 2 ที่ใน `db/schema.py` (~477 และ ~820) คอลัมน์ไม่ตรงกัน (ตรวจว่าคอลัมน์ `status`, `organization_id`, `author` มีจริง)
- เรียกใช้จาก `app_server.py` ~บรรทัด 986 (ตัวตั้งเวลาเบื้องหลัง?) ตรวจว่ารันแล้ว error ถี่ๆ ลง log หรือไม่
**แนวทางแก้:**
1. เปลี่ยนเป็น import แบบเดียวกันทุกที่ (`from database import _get_conn`) หรือใช้ helper ที่มี fallback ทั้งสองแบบให้ครบทุกจุด
2. เทียบ SQL กับ schema จริง (เปิดฐานชั่วคราวที่สร้างจาก `db/schema.py` แล้วรันคำสั่ง) แก้ชื่อคอลัมน์/ตารางให้ตรง ใช้ `with` หรือ `finally` ปิด connection ให้ครบทุกทาง
3. ตรวจรูปแบบที่ AI ตอบกลับ (JSON list) ว่า parse ปลอดภัย ไม่พังเมื่อ AI ตอบไม่เป็น JSON
4. ถ้าฟีเจอร์นี้ถูกเรียกอยู่ในตัวตั้งเวลา ให้แน่ใจว่าไม่กินโควตา AI โดยไม่จำเป็น
**ทดสอบ:** เทสต์ใหม่ `tests/test_knowledge_harvester.py` ด้วย DB ชั่วคราว + mock `generate_response` (ห้ามเรียก AI จริง): ไม่มีข้อความ = คืน None, มีข้อความ = สร้าง draft ใน `wiki_pages`, AI ตอบขยะ = ไม่พัง, import แบบ top-level ทำงานได้

## ข้อ 5: หน้าแชทดึงข้อมูลถี่และวาดใหม่ทั้งหมด
**ตำแหน่ง:** `static/js/chat.js` — ค้น `setInterval` (ตัวอย่าง: feed โพล 15 วิ ~บรรทัด 1690, global poller 30 วิ ~3969) และฟังก์ชันที่ดึงข้อความแชท (ค้นตัวที่ยิง `/api/chat/messages/` ทุก ~3000 ms) พร้อมฟังก์ชัน render ที่ล้าง `innerHTML` ทั้งรายการ
**หมายเหตุ:** ตอนนี้ข้อความมาทาง socket แบบเรียลไทม์แล้ว การโพลทุก 3 วิควรเป็นแค่ตัวสำรอง
**แนวทาง (ทำเฉพาะที่ปลอดภัย):**
1. หาตัวโพลแชทจริง ยืนยันด้วยการดู Network ในเบราว์เซอร์ทดสอบ ก่อนแก้
2. ถ้า socket เชื่อมต่ออยู่ → ลดความถี่โพลเหลือ ~20–30 วิ (หรือหยุดชั่วคราว) เมื่อ socket ตัด/ไม่ได้โฟกัสแท็บ (`document.hidden`) ให้กลับมาโพลถี่ขึ้น
3. เปลี่ยนการวาดเป็นแบบ **เพิ่มเฉพาะข้อความใหม่** (เทียบ id ล่าสุด) แทนการล้างและวาดทั้งหมด ต้องไม่ทำให้สกอลล์กระโดด ไม่ทำให้ข้อความที่กำลังเลือก/พิมพ์หาย และ **ยังต้องอัปเดตสถานะข้อความเดิม** (อ่านแล้ว, ลบ, แก้ไข, ตอบกลับ, รีแอคชัน) ถ้าทำไม่ได้ปลอดภัย ให้เทียบแฮชผลลัพธ์แล้ววาดใหม่เฉพาะเมื่อมีการเปลี่ยนจริง
4. ห้ามกระทบ optimistic send, typing indicator, สถานะออนไลน์, เสียง/แจ้งเตือนข้อความใหม่ (ซ้ำเสียงไม่ได้)
**ทดสอบ:** เปิดสองบัญชี (ทริก origin คนละอัน localhost vs 127.0.0.1 บนเซิร์ฟเวอร์ทดสอบ) ส่งข้อความ/ลบ/แก้ไข/รีแอคชัน ดูว่าอัปเดตครบ, สกอลล์ไม่กระโดด, จำนวนคำขอใน Network ลดลงชัดเจน (วัดก่อน/หลัง), เทสต์เดิม `test_chat_*` ผ่านทีละไฟล์

## ข้อ 6: ตัวแปรในหน่วยความจำไม่เคยถูกล้าง
**ตำแหน่ง (dict ระดับโมดูลที่โตได้ ตรวจแล้ว):**
- `routes/chat.py`: `_line_batch_timer`, `_typing_status`, `_limit_warn_cache`, `_kb_filenames_cache`, `_profile_cache` (~912), `_typing_last` (~2220), `_rtc_last_offer` (~2386), `_pending_calls` (~2392)
- `routes/line_webhook.py`: `_line_batch_timer`, `_typing_status`, `_limit_warn_cache`, `_PROCESSED_WEBHOOK_EVENTS` (~603)
- `routes/auth.py`: `_qr_tokens` (~53, legacy), `_RECENT_LINE_CALLBACK_CACHE` (~3995)
- `routes/shared.py`: `_OAUTH_STATES`, `_RECENT_POPPED_STATES` (~114)
- `routes/admin.py`: `_DASHBOARD_CACHE`, `_recon_cache`; `routes/social.py`: `_MAPS_SEARCH_CACHE`, `_MAPS_REVERSE_CACHE`; `db/org_security.py`: `_CACHE`
**แนวทาง:**
1. ตรวจทีละตัวว่าโตตามอะไร (ต่อผู้ใช้/ต่อคำค้น/ต่อ event) และมีการลบเองอยู่แล้วหรือไม่ (บางตัวมี TTL แต่ไม่เคยลบคีย์หมดอายุ)
2. ทำตัวช่วยกลาง เช่น `routes/_memcache.py` : `prune(d, ttl, now, max_items)` ลบรายการหมดอายุและจำกัดจำนวนสูงสุด (ตัดรายการเก่าสุด) ใช้ lock ถ้าถูกเข้าถึงจากหลายเธรด (เซิร์ฟเวอร์ใช้ `async_mode='threading'`)
3. เรียก prune แบบ **ถูกๆ** : ตอนเขียนลง dict ทุก N ครั้ง หรือเธรดเบื้องหลังเดียวทุก 5–10 นาที (ถ้ามีตัวตั้งเวลาอยู่แล้วให้ใช้ตัวเดิม) ห้ามสร้างเธรดใหม่ไร้ขอบเขต
4. **ห้ามลบข้อมูลที่ยังใช้งาน** — `_pending_calls` ต้องเคารพ TTL 45 วิของสายค้าง, `_PROCESSED_WEBHOOK_EVENTS` ต้องเก็บนานพอกัน webhook ซ้ำ (ตรวจ TTL ที่โค้ดใช้เทียบอยู่ก่อน), `_typing_status` ต้องไม่ตัดตอนกำลังพิมพ์
5. ตัวที่ไม่ใช้แล้ว (`_OAUTH_STATES`, `_qr_tokens`) ตรวจว่าไม่มีใครอ้างถึงก่อนลบ ถ้ามีคนอ้างให้คงไว้
**ทดสอบ:** เทสต์หน่วยของ `prune` (หมดอายุถูกลบ, ยังไม่หมดอายุอยู่, เกินขีดจำกัดตัดเก่าสุด), เทสต์ `tests/isolated/calls_scenarios.py` และ `presence_scenarios.py` ที่มีอยู่ต้องยังผ่านทั้งหมด (สายค้าง/การพิมพ์/สถานะต้องไม่พัง), ยิงสร้างรายการ 10,000 รายการแล้วเห็นว่าขนาดไม่เกินขีดจำกัด

## ข้อ 7: CSP ยังมี `unsafe-inline`
**ตำแหน่ง:** `app_server.py` ~บรรทัด 419–433 (`script-src` และ `style-src`)
**ความจริงที่ต้องรู้:** เทมเพลตมี inline script และ inline handler (`onclick=`, `oninput=`) จำนวนมาก (หลายพันบรรทัดใน `index.html`) การถอด `'unsafe-inline'` ตรงๆ = **เว็บพังทั้งหน้า** ห้ามทำแบบนั้น
**แนวทาง (ค่อยเป็นค่อยไป ปลอดภัยก่อน):**
1. **ระยะที่ 1 (ทำได้เลย ความเสี่ยงต่ำ):** เพิ่มโหมด **Report-Only** ผ่านตัวแปร env (`CSP_REPORT_ONLY=1`) ส่งหัว `Content-Security-Policy-Report-Only` ที่เข้มงวด (ไม่มี `unsafe-inline`) ควบคู่กับของเดิม และเพิ่ม endpoint รับรายงานการละเมิด (`/api/csp-report` จำกัดอัตรา บันทึกแบบย่อ) เพื่อวัดว่ามีกี่จุดที่ต้องแก้ โดยไม่กระทบผู้ใช้
2. **ระยะที่ 2 (ประเมินแล้วค่อยทำ):** ใช้ nonce ต่อคำขอสำหรับ `<script>` inline และย้าย inline event handler ไปเป็น `addEventListener` ทีละหน้า — งานใหญ่ ให้ทำเฉพาะหน้า login/เข้าสู่ระบบก่อนถ้าเวลาไม่พอ และ **แจ้งผู้ใช้ว่างานเต็มจะใช้เวลา** อย่ารีบถอด `unsafe-inline` ก่อนสอบ
3. ทางเลือกลดความเสี่ยงเพิ่มโดยไม่พังเว็บ: คง `unsafe-inline` ไว้ แต่เพิ่ม `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'self'`, `form-action 'self'` (ตรวจว่ามีอยู่แล้วหรือยังก่อน อย่าเพิ่มซ้ำ)
**ทดสอบ:** เปิดทุกหน้าหลักด้วย Report-Only แล้วนับรายงาน, ยืนยันว่าหน้าเดิมทำงานปกติ (Console ไม่มี CSP error ในโหมดบังคับ), ไม่ทำให้ Stripe/Google/Socket.IO/CDN ที่ใช้อยู่ถูกบล็อก

## ข้อ 8: เครื่องมือ fuzz (`tools/fuzz_routes.py`) รันไม่จบ (database is locked)
**ที่มา:** สคริปต์ยิง input แปลกๆ ใส่ทุก route บน DB ชั่วคราว แล้วเกิด `database is locked` ถี่จนไม่จบ (SQLite WAL, busy_timeout 60000 ms ทำให้ค้างนาน)
**แนวทาง:**
1. สืบสาเหตุก่อนแก้: ใช้ log ดูว่าเป็นเธรดเบื้องหลังของแอป (ตัวตั้งเวลา, เธรด `_deferred`, presence) แย่ง DB กับ request ที่ fuzz หรือเป็นการเปิด connection ค้าง (ไม่ปิด) ใน route บางตัว — ถ้าเป็น **connection leak ใน route จริง นั่นคือบัคของแอป** ให้บันทึกชื่อ route และแก้ (ใช้ `try/finally` ปิด connection)
2. ในโหมด fuzz: ปิดเธรดเบื้องหลัง/ตัวตั้งเวลาด้วยตัวแปร env, ตั้ง `busy_timeout` ต่ำ (เช่น 2000 ms) เพื่อให้ล้มเหลวเร็วแทนค้าง, ตั้งเวลารวมสูงสุดและเวลาต่อ route, รันทีละ route ต่อเนื่องไม่ขนาน
3. ให้สคริปต์พิมพ์ความคืบหน้าและสรุปผลเป็นระยะ (ไม่เงียบ) และเขียนผลลงไฟล์รายงานเมื่อหมดเวลา/ถูกขัดจังหวะ
4. รันให้จบหนึ่งรอบ แล้วจัดกลุ่มผล (HTTP 500 / exception ที่ไม่ได้ดักจับ) ตามชนิดและตำแหน่งโค้ด แก้เฉพาะที่เป็นบัคจริงและเกี่ยวกับ input ที่ผู้ใช้ส่งได้ ส่วนที่กำกวมให้รายงานผู้ใช้ก่อนแก้
5. ข้าม endpoint ทำลายข้อมูลตามเดิม (สคริปต์มีรายการข้ามตามชื่ออยู่แล้ว ห้ามลดรายการนั้น)
**ทดสอบ:** รัน fuzz ให้จบด้วย DB ชั่วคราว ได้รายงานสรุป, ไม่มีการแตะ `chat_history.db` จริง, ปิดโปรเซสทดสอบทุกตัวเมื่อเสร็จ
