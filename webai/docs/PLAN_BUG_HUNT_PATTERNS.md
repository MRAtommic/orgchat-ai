# แผนล่าบั๊ก "จุกจิก" แบบเป็นระบบ (Bug Hunt by Pattern) — สำหรับ anti

ผู้ใช้เจอบั๊กเล็กๆ ระหว่างใช้งานจริงบ่อยมาก แทบทุกครั้งที่ลองใช้ฟีเจอร์ใหม่ รอบที่ผ่านมาเราแก้ได้ทีละจุดหลังผู้ใช้เจอ **เป้าหมายรอบนี้: หาบั๊กประเภทเดียวกัน (และประเภทอื่น) ให้เจอก่อนผู้ใช้ โดยไล่ทั้งโค้ดแบบมีระบบ ไม่ใช่รอให้เจอเอง**

กฎเหล็กเดิมใช้ทั้งหมด: ห้ามอ่าน/commit `.env`, ห้าม push, ใช้ DB/KB ชั่วคราว, เคลียร์ secret ภายนอกก่อนรันเซิร์ฟเวอร์ทดสอบ, pytest ทีละไฟล์, ปิดเซิร์ฟเวอร์ทดสอบเมื่อเสร็จ, ทุกบั๊กที่แก้ต้องมี regression test ที่ล้มเมื่อใช้โค้ดเดิม, **ก่อนเขียนว่า "ผ่าน" ต้องรันจริงและแปะบรรทัดสรุป pytest** (รอบก่อนรายงานเกินจริงมาแล้วหนึ่งครั้ง)

## วิธีทำงาน

สำหรับแต่ละ "ประเภทบั๊ก" ด้านล่าง: (1) ใช้วิธีค้นหาที่ระบุ ไล่ **ทั้งโปรเจกต์** ไม่ใช่แค่ไฟล์ตัวอย่าง (2) รายการที่เจอเขียนลงตาราง `docs/BUG_HUNT_FINDINGS.md` (ประเภท / ไฟล์:บรรทัด / อาการที่ผู้ใช้จะเห็น / ความรุนแรง P0–P3 / สถานะ) (3) แก้ + เทสต์ (4) ถ้าเจอบั๊กซ้ำประเภทเดิมในหลายที่ ให้แก้แบบรวมศูนย์ (helper เดียว) ไม่แก้กระจัดกระจาย

## ประเภทที่ 1: ระบบ "ตกไปใช้ค่า/ผู้ใช้เริ่มต้น" เมื่อหาไม่เจอ (Silent fallback identity)

เคยเกิดจริง: LINE Login หาบัญชีไม่เจอแล้วตกไปเป็นบัญชี "few/Admin" (ใครมี LINE ก็ได้สิทธิ์ผู้ดูแล); `database.get_user_setting()` คืน dict ค่าเริ่มต้นเสมอ (truthy) แม้ไม่มีผู้ใช้ → ลูป `while` ไม่จบ, เช็ค "มีผู้ใช้ไหม" ผิด; Google callback เรียกฟังก์ชันที่ไม่มีอยู่ (`database.get_user`)
**วิธีหา:**
- grep ทุกฟังก์ชัน `get_*` ที่คืนค่าเริ่มต้นแทน `None` (เริ่มจาก `get_user_setting`, `get_org*`, `get_app_setting`) แล้วไล่ทุกจุดที่เรียกใช้ว่า **ใช้ผลลัพธ์เป็นเงื่อนไข "มี/ไม่มี" หรือไม่** (ผิดทุกจุดที่ทำแบบนั้น)
- grep `or "admin"`, `or "user"`, `or 'default'`, `.get("role", "admin")`, `default_org`, ค่า fallback ที่เป็นบัญชีจริงหรือสิทธิ์สูง
- ทุก flow ล็อกอิน/ผูกบัญชี (รหัสผ่าน, Google, LINE, QR, magic link, เชิญสมาชิก): ทำตาราง "ผู้ใช้อยู่ในสถานะไหนบ้าง" (ไม่มีบัญชี / มีแต่ไม่มีองค์กร / ผูกแค่ bot ID / ผูกแค่ login ID / ผูกทั้งคู่ / ถูกปิดใช้งาน / ผูกกับบัญชีอื่น) × ช่องทาง แล้วเขียนเทสต์ให้ครบทุกช่อง ผลต้องเป็น "ถูกต้อง" หรือ "ข้อความชี้ทางที่เข้าใจ" ห้ามสร้างบัญชีเปล่าเงียบๆ

## ประเภทที่ 2: ตัวระบุสองชุดที่ไม่ตรงกัน (Identity mismatch)

เคยเกิดจริง: LINE Login กับ LINE Messaging bot ให้ user ID คนละค่า (`line_login_id` vs `line_user_id`) ผูกฝั่งหนึ่งแล้วอีกฝั่งหาไม่เจอ → ผู้ใช้ล็อกอินแล้วได้บัญชีใหม่เปล่า; Google email vs username; `org_id` vs `organization_id`
**วิธีหา:**
- ไล่ทุกคอลัมน์ที่เก็บ "ตัวระบุภายนอก" (`line_*`, `google_*`, email, phone) ว่าอ่าน/เขียนที่ไหน และทุกที่ใช้ตัวไหนค้นหา เทียบกันเป็นตาราง (เขียนที่ไหน / ค้นด้วยอะไร) หาจุดที่เขียนแบบหนึ่งแต่ค้นอีกแบบ
- ตรวจ case-sensitivity (`COLLATE NOCASE`), ช่องว่างหัวท้าย, ค่า NULL กับสตริงว่าง `''` (UNIQUE/เปรียบเทียบพลาด)
- หลังผูก/ยกเลิก/ย้ายบัญชี ทุกหน้าที่แสดงสถานะ ("ผูกแล้ว/ยังไม่ผูก") ต้องตรงกับ DB — เขียนเทสต์ end-to-end ผูก→ดูสถานะ→ยกเลิก→ดูสถานะ→ผูกใหม่ ของทั้ง LINE bot, LINE Login, Google

## ประเภทที่ 3: ด่านตรวจ/early return ที่ข้ามงานจริง (Guard skipping the real work)

เคยเกิดจริง: `line_login_callback` เจอ "ล็อกอินอยู่แล้ว" แล้ว redirect กลับหน้าแรกทันที → กดเชื่อม LINE Login จากหน้าตั้งค่าแล้ว **ไม่เคยบันทึกการผูก**
**วิธีหา:**
- grep `return redirect(`, `return jsonify(...)` ที่อยู่ **ต้นฟังก์ชัน** ก่อนจะทำงานหลัก (callback, bind, link, confirm, webhook handler) ตรวจว่าเงื่อนไขนั้นครอบคลุม "กรณีที่ควรทำงานต่อ" ไหม (เช่น ล็อกอินอยู่ + โหมดผูก, token ใช้แล้วแต่ยังต้องแสดงผลสำเร็จ)
- ทุก endpoint OAuth/callback/magic-link: ทดสอบ 4 สถานะ = ล็อกอินอยู่/ไม่ล็อกอิน × โหมดผูก/โหมดล็อกอิน, รวม callback ซ้ำ (refresh/กด back), state หมดอายุ/ใช้แล้ว

## ประเภทที่ 4: ข้อผิดพลาดถูกกลืน หรือแสดงเป็นข้อความที่ไร้ประโยชน์ (Swallowed / opaque errors)

เคยเกิดจริง: popup "ส่งไม่สำเร็จ — internal_error"; toast แดงค้างในหน้า Drive "เชื่อมต่อแล้ว"; `except sqlite3.OperationalError: pass`
**วิธีหา:**
- grep `except Exception: pass`, `except: pass`, `except ...: continue/return None` ทั้งโปรเจกต์ ไล่ทีละจุดว่า "กลืนแล้วผู้ใช้เห็นอะไร" ที่ควร log ให้เพิ่ม `logger.exception`/`warning` ที่ไม่ใส่ secret
- grep `"internal_error"`, `"error": str(e)`, `jsonify({"error"` ที่ส่งข้อความดิบ/ชื่อ exception ให้ผู้ใช้เห็น → ทำตาราง code→ข้อความไทยที่เข้าใจได้ และให้ฝั่ง JS แสดงข้อความจากตารางนั้น (ไม่ใช่ code ดิบ) พร้อมระบุว่าผู้ใช้ควรทำอะไรต่อ
- หา popup "ส่งไม่สำเร็จ internal_error" ให้เจอต้นตอ: grep ข้อความ "ส่งไม่สำเร็จ" ใน `static/js` และ `templates` ไล่ว่าเรียก endpoint ไหน แล้วทำให้ endpoint นั้นล้มได้ทุกแบบในเทสต์เพื่อดูว่าแสดงอะไร
- Playwright crawl ทุกหน้า ทุกเมนู บันทึก **console error / warning / network 4xx-5xx** ทั้งหมด ทำตาราง (หน้า / เหตุการณ์ / URL / สถานะ) — ถ้าหน้าไหนมี toast error ค้างหรือ request 4xx/5xx โดยผู้ใช้ไม่ได้ทำอะไรผิด ถือเป็นบั๊ก

## ประเภทที่ 5: UI กับ API/ข้อมูลไม่ตรงสัญญา (Frontend–backend contract drift)

เคยเกิดจริง: ตาราง audit อ่าน `row.event_type` แต่ API ส่ง `action` (ต้องรองรับสองชื่อ); `submitDirectLineBind` ส่ง field ผิดชื่อ
**วิธีหา (ทำเป็นสคริปต์อัตโนมัติได้):**
- สกัด URL ที่ `fetch(`/`$.ajax`/`XMLHttpRequest` ทุกจุดใน `static/js/**` และ `templates/**` แล้วเทียบกับ route ที่ลงทะเบียนจริง (`app.url_map`) — URL ที่ไม่มี route, method ไม่ตรง = บั๊ก
- สำหรับแต่ละ endpoint ที่ UI ใช้: เทียบ field ที่ JS อ่านจาก JSON (`data.xxx`, `row.xxx`) กับ field ที่ route ส่งกลับจริง (เรียกด้วยข้อมูลทดสอบ) — field ที่ JS อ่านแต่ไม่มีใน response = บั๊ก (จะแสดง `undefined`/ว่าง)
- ทุก `onclick="fn()"`/`addEventListener` ในเทมเพลต: ฟังก์ชัน `fn` ต้องมีจริง (ปุ่มตายเงียบ) — เขียนสคริปต์ตรวจชื่อฟังก์ชันที่ถูกเรียกจาก HTML เทียบกับที่ประกาศใน JS
- ID/selector ที่ JS ใช้ (`getElementById`, `querySelector`) ต้องมีใน HTML จริง
- ตรวจ API ที่ส่ง HTML/ข้อความผิดชนิด (JSON คาดแต่ได้ HTML error page → `Unexpected token <`)

## ประเภทที่ 6: เรียกฟังก์ชัน/ตัวแปร/คอลัมน์ที่ไม่มี (Undefined names / schema drift)

เคยเกิดจริง: Google callback เรียก `database.get_user` ซึ่งไม่มี → ล้มตอนรัน
**วิธีหา:**
- รัน `python -m pyflakes .` (หรือ `ruff check --select F821,F811,F401,F841 .`) ทั้งโปรเจกต์ ผลลัพธ์ F821 (undefined name) ทุกจุดต้องแก้ทั้งหมด
- เขียนสคริปต์ AST ตรวจว่า `database.<name>` / `db.<module>.<name>` ที่ถูกเรียกมีอยู่จริงในโมดูล
- เทียบชื่อตาราง/คอลัมน์ใน SQL ทุกข้อความ (`SELECT/INSERT/UPDATE`) กับ schema จริง (สร้าง DB ชั่วคราวด้วย migration แล้วรัน `PRAGMA table_info`) — คอลัมน์ที่ใช้แต่ไม่มี หรือ migration ที่ไม่ครบบน DB เก่า (ทดสอบ DB เวอร์ชันเก่าที่ผู้ใช้มีจริง โดยอัปเกรดสำเนา)
- `tests/test_fresh_db_migrations.py` ต้องครอบคลุมทุกคอลัมน์ใหม่

## ประเภทที่ 7: เงื่อนไขแข่งกันและงานค้าง (Race / stuck state)

เคยเกิดจริง: อัปโหลดหลายไฟล์พร้อมกันทำให้สถานะค้าง INDEXING (read-modify-write ของ `file_meta.json`); callback LINE ซ้ำ (double request)
**วิธีหา:**
- ไล่ทุกที่ที่ "อ่านไฟล์/แถว → แก้ในหน่วยความจำ → เขียนกลับ" (JSON meta, settings, counters, quota, session) ว่าอยู่ใต้ lock/transaction หรือไม่ ทดสอบยิงพร้อมกัน 20–50 เธรด
- ทุก "สถานะระหว่างทาง" (INDEXING, PENDING, processing, token ยังไม่ใช้) ต้องมีทางออก: ตอนสตาร์ตแอปให้กวาดสถานะค้างเก่ากว่า X นาทีเป็น FAILED/ลองใหม่ + ทดสอบ restart กลางงาน
- ปุ่มที่กดซ้ำได้ (ส่ง, ผูก, อัปโหลด, อนุมัติ) ต้องกันกดซ้ำฝั่ง UI และฝั่ง server (idempotent)
- SQLite `database is locked` ภายใต้โหลด, ตรวจ busy_timeout/WAL บน Windows + โฟลเดอร์ OneDrive (เคยมี disk I/O error)

## ประเภทที่ 8: ข้อความไทย/URL/การเข้ารหัส (Encoding)

เคยเกิดจริง: LINE "Invalid action URI" เพราะชื่อไฟล์ภาษาไทยในลิงก์ไม่ถูก encode; markdown `**` โผล่ใน LINE
**วิธีหา:**
- ทุกที่ที่สร้าง URL จากข้อมูลผู้ใช้ (ชื่อไฟล์, ชื่อองค์กร, คำค้น) ต้อง `urllib.parse.quote`/`urlencode` — grep f-string ที่ต่อ URL
- ทดสอบทุกช่องข้อมูลด้วยชุดข้อความ: ไทยล้วน, ไทยปนอังกฤษ, emoji, อักขระควบคุม, ยาว 5,000+ ตัว, `' " < > & % # ? / \`, `../`, ชื่อไฟล์ซ้ำ, Unicode normalization (สระ/วรรณยุกต์สลับ) — ตรวจการบันทึก การแสดงผล การค้นหา การส่งออก
- ทุกข้อความที่ส่งไป LINE: ความยาว, จำนวนข้อความ, ชนิด, URI ที่ valid, ไม่มี markdown ดิบ

## ประเภทที่ 9: CSS/ธีม/เลย์เอาต์ที่กระทบกันทั้งหน้า (Global style bleed)

เคยเกิดจริง: `.hidden{display:none!important}` ทับ `md:flex` ซ่อนปุ่มบนจอใหญ่ ~23 จุด; ปฏิทินเตี้ยเพราะ Tailwind ที่คอมไพล์ไว้ไม่มีคลาสที่ใช้; แหล่งอ้างอิงหายเพราะ `.hidden !important`
**วิธีหา:**
- grep `!important` ทั้ง `static/**/*.css` ไล่ว่ากฎไหนกว้างเกินไป (selector สั้น/ครอบทั้งหน้า)
- เขียนสคริปต์: ดึงคลาสทั้งหมดที่ใช้ใน templates/JS เทียบกับคลาสที่มีใน `tailwind.css` ที่คอมไพล์ — คลาสที่ใช้แต่ไม่มี = บั๊ก (rebuild ด้วย `npx tailwindcss@3.4.16 ...` ที่ `tools/tailwind` แล้วเพิ่ม `?v=`)
- Playwright ถ่ายภาพทุกหน้า × (375, 768, 1024, 1360, 1920) × (สว่าง/มืด) ตรวจ element ล้นกรอบ/ทับกัน/ตัดคำ/แถบเลื่อนซ้อน (ใช้สคริปต์ตรวจ `scrollWidth > clientWidth`, element นอก viewport, ข้อความ overflow) แล้วดูภาพประกอบ
- `getComputedStyle().display` ของทุก element ที่มีคลาส `hidden ...:` ที่ทุกความกว้าง (ตารางผล)

## ประเภทที่ 10: พฤติกรรม AI/พรอมต์ (LLM behavior)

เคยเกิดจริง: ตอบยาวและเสนอตัวช่วยหลายข้อ, แนบแหล่งอ้างอิง 3 ไฟล์ทั้งที่ใช้ 1, ตอบ "แบนด์อะไร" ไม่ได้เพราะ retrieval พิมพ์ผิด, ไม่ตัดคำทักทายออกจากประวัติ
**วิธีหา (ใช้ mock โมเดล + retrieval จริงบน KB ชั่วคราว):**
- ชุดคำถามทดสอบ 60+ ข้อ (ตรง/พิมพ์ผิด/คำพ้อง/ถามต่อเนื่อง/ทักทาย/นอกเรื่อง/ถามข้อมูลที่ไม่มี/ถามข้อมูลของหมวดที่ไม่มีสิทธิ์/prompt injection ในเอกสารและในคำถาม) วัด: ได้ไฟล์ที่ถูกไหม, แหล่งอ้างอิงตรงไหม, `select_cited_sources` ตัดผิด/ตัดขาดไหม
- ตรวจ prompt ที่ประกอบจริง (ไม่ใช่แค่ที่เขียนไว้) ว่ามีกฎครบและไม่ขัดกัน (เว็บ vs LINE) ความยาวไม่เกินโควตาโทเค็น
- prompt injection: เอกสารที่มีข้อความ "ละเว้นคำสั่งก่อนหน้า..." ต้องไม่ทำให้บอทรั่วข้อมูลหรือเปลี่ยนพฤติกรรม

## ประเภทที่ 11: สิทธิ์/องค์กร (Authz leaks) — ทดสอบแบบตาราง

เคยมีเสี่ยง: ผู้ใช้ที่ไม่มีสิทธิ์หมวดหมู่เห็นไฟล์ผ่าน LINE; admin ตัดการเชื่อม Drive ไม่ได้
**วิธีหา:** สร้างตารางอัตโนมัติ (endpoint ทุกตัว × บทบาท owner/admin/member/ไม่ล็อกอิน/คนละองค์กร × ผลที่ควรได้) แล้วรันเทียบ — ทุกช่องที่ไม่ตรงคือบั๊ก; IDOR โดยเปลี่ยน id ในทุกพารามิเตอร์

## ประเภทที่ 12: ข้อมูลจริงของผู้ใช้ "สกปรก" ไม่เหมือนข้อมูลทดสอบ

ผู้ใช้ใช้ DB จริงที่ผ่านการอัปเกรดหลายรอบ: บัญชีเก่าไม่มีองค์กร, ค่า NULL, ผู้ใช้ซ้ำ, บัญชีเปล่าที่ถูกสร้างจาก LINE Login รอบก่อน, ไฟล์ meta ไม่ตรง vector store (เคย JSON 109 ท่อน vs meta 315)
**วิธีหา:** ทำสำเนา DB/ข้อมูลทดสอบที่ "สกปรก" ด้วยสคริปต์ (ผู้ใช้ไม่มีองค์กร, องค์กรไม่มีเจ้าของ, ผู้ใช้ซ้ำตัวพิมพ์ต่างกัน, line id ซ้ำ, NULL ทุกคอลัมน์ที่เป็นไปได้, meta ชี้ไฟล์ที่ไม่มีแล้ว) แล้วเปิดทุกหน้า/เรียกทุก API ดูว่าพังหรือไม่ — **ห้ามใช้ DB จริงของผู้ใช้**; ให้เขียนเครื่องมือตรวจความสอดคล้อง `tools/check_data_consistency.py` ที่ผู้ใช้รันกับข้อมูลจริงแบบอ่านอย่างเดียวได้เอง (รายงานบัญชีเปล่า/ซ้ำ/ไฟล์ meta ไม่ตรง vector store พร้อมวิธีแก้ ไม่แก้ให้อัตโนมัติ)

## ประเภทที่ 13: โครงสร้างพื้นฐานจริง (Tunnel/โดเมน/คุกกี้)

ผู้ใช้เข้าผ่าน Cloudflare Tunnel (`openchat.sbs`) และบางครั้ง localhost: OAuth state หายข้ามโดเมน, คุกกี้ SameSite=Lax ข้ามไซต์, redirect_uri ไม่ตรง, IP ใน audit เป็นของ tunnel
**วิธีหา:** ทบทวนทุกจุดที่สร้าง absolute URL (redirect_uri, ลิงก์ในการ์ด LINE, ลิงก์ดาวน์โหลด) ว่ามาจาก config เดียวกัน; จำลอง header `X-Forwarded-*`/`CF-Connecting-IP`; ทดสอบ flow OAuth เมื่อเริ่มที่ localhost แล้วกลับที่โดเมนสาธารณะ

## ส่วนมือถือ/สถานการณ์ผู้ใช้จริง (ทำหลังผ่านประเภทข้างต้น)

เดินตามสถานการณ์เหมือนผู้ใช้จริงใน Playwright (Chrome จริง, พอร์ตทดสอบ): ผู้ใช้ใหม่ทั้งเส้นทาง · ผู้ใช้เก่าที่ผูกแล้ว/ยกเลิกแล้ว/ผูกใหม่ · admin จัดการสมาชิก/สิทธิ์/KB · member ถามแชท/ค้นไฟล์ · เปิดค้างข้ามคืนแล้วกลับมาใช้ (session หมดอายุ) · สลับแท็บ/เครื่อง · ย้อนกลับ/รีเฟรชกลางทุกขั้นตอน · เน็ตช้า/ตัด (throttle) — ทุกครั้งที่ผิดปกติ บันทึกภาพ+ขั้นตอน

## ส่งมอบ

1. `docs/BUG_HUNT_FINDINGS.md` — ตารางบั๊กทุกข้อ (ประเภท 1–13) พร้อมสถานะ: **ยืนยันแล้ว / แก้แล้ว-ยืนยันแล้ว / แก้แล้ว-ยังไม่ยืนยัน / ไม่แก้ (เหตุผล)**
2. โค้ดที่แก้ + regression test (รันได้ทีละไฟล์) + สคริปต์ตรวจอัตโนมัติที่เขียนขึ้น (contract check, undefined names, tailwind class coverage, authz matrix) เก็บไว้ใน `tools/` หรือ `tests/` ให้รันซ้ำได้
3. ตารางผลรัน pytest จริงทุกไฟล์ (ชื่อไฟล์ / บรรทัดสรุป / เวลา)
4. รายการที่ anti ทำไม่ได้เพราะต้องใช้ LINE/Google/AI จริง พร้อมขั้นตอนให้ผู้ใช้ทดสอบเป็นข้อๆ
5. รายการสิ่งที่ผู้ใช้ต้องทำเอง (restart เซิร์ฟเวอร์, Ctrl+F5, Issue LINE Login secret ใหม่ ฯลฯ)
